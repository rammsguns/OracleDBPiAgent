# WP-30B-CHECK-WEB-AGENT

Branch: `wp-30b-check-web-agent`. Built on merged WP-30A (`9b3b74a`).

## Delivered

The web **Check** tab runs the WP-30A engine only after its button is pressed. It supports a single configured target or all configured targets, reads the same private threshold configuration as the CLI, and displays Target, Check, Status, Value, Threshold WARN/CRIT, Scope, Drill down and Note. Its header shows the engine's aggregate worst status, effective-status counts and selected targets. SKIPPED rows remain visible and do not contribute to counts. Table values and headings use the existing `textContent` helper. Status labels remain readable without colour; Playwright verifies at least 4.5:1 text contrast in both themes, at desktop and phone widths. Wide evidence scrolls inside its own keyboard-focusable region.

`GET /api/check?target=NAME` returns `{result: CheckRun}`. `target=__all_targets__` selects all configured targets; that sentinel cannot collide with a validated target name. The route shares Top's bearer/Host/Origin protection, insight concurrency lock, disconnect cancellation, provider cleanup and 1 MiB serialized-response cap. Cancel and target changes abort the browser request and discard late responses. Native operations finish before provider cleanup or lock release; cancellation prevents subsequent native queries. The Check selector honours the product's configured owner-approved aliases. Worker live verification used only the two packaged labs; synthetic alias tests used fake providers.

The `health_check` tool uses the current/pinned target, with only the existing optional `target` parameter. It runs the same sequential, read-only, statement-timeout-bounded engine. A single summary line provides status, counts, target and capture time, explicitly describing point-in-time and windowed probes. Subsequent lines contain non-OK checks with values, scopes, drill-down commands and notes. An UNKNOWN observation explicitly mapped to OK by policy is also shown, so policy cannot silently hide missing evidence. SKIPPED rows are explicit. Ordinary OK rows are omitted. The entire serialized result, including details, is byte-capped and credential-redacted. Probe audits remain engine-owned; the tool also audits completion/failure without raw error messages or binds. Abort/configuration failures throw; missing grants remain UNKNOWN observations.

Tool description (138 characters):

> Check database health against configured thresholds. Returns a summary and non-OK checks from read-only point-in-time and windowed probes.

Serialized schema (88 characters; no `required` list, so `target` is optional):

```json
{"type":"object","properties":{"target":{"type":"string"}},"additionalProperties":false}
```

Serialized name/description/parameters together: **280 characters**. The guidance addition is **113 characters**, including its newline:

> Database health questions: use health_check for the current target; report UNKNOWN and probe/window limitations.

The historical prompt/schema fixtures remain intact: their tests isolate this explicit addition, while a separate assertion caps its growth and verifies the guidance is present.
